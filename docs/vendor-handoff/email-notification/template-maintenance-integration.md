# 郵件通知與「訊息範本維護」連動規格

更新日期：民國 115 年 10 月 12 日。

**資訊公司須將通報完成通知整合至既有「系統管理 → 訊息範本維護」。**郵件主旨與內文由該功能管理，寄信程式依範本代碼讀取並帶入案件資料，不能另外維護一套寫死於寄信程式的通知文字。

本文件是正式系統的建置需求。郵件連動這部分僅更新交付文件，未於主系統接入範本儲存或寄信服務，Q32 亦未登錄至公開 Q&A。

## 既有功能及欄位對應

已核對原型的 `getMsgTemplateViewHtml()` 與 `openMsgTemplateDialog()`，目前有以下欄位：

- **名稱（name）**：危險作業通報完成通知。
- **標題（subject）**：郵件主旨，使用 `【TOiRA 危險作業通報】通報完成｜{CASE_NO}｜{WORK_NAME}`。
- **代碼（code）**：建議固定為 `HAZARD_REPORT_SUBMITTED`，供通報完成事件選用；名稱可編輯，已綁定的代碼應保持穩定。
- **訊息類型（type）**：電子郵件。現有新增／編輯對話框使用 `EML`；列表及示範資料使用 `EMAIL`。資訊公司須統一儲存代碼與顯示名稱，避免範本新增後無法被查詢或寄信服務找到。交付種子資料暫採 `EML`。
- **說明（desc）**：平台成功收到危險作業通報後，通知填報者並副知管轄勞動檢查機構。
- **內容（content）**：帶參數的純文字郵件內容，沿用目前 `{CASE_NO}` 形式的參數代換。

正式版須支援 HTML 與純文字內容、範本預覽、啟用／停用及版本紀錄。這些是需建置或確認的功能，不能將目前單一內容文字框視為已具備全部功能。HTML 內容可增設對應欄位或採既有服務支援的儲存方式，但須由同一個「訊息範本維護」管理。

目前原型的搜尋、新增、修改及刪除主要是展示提示，沒有正式範本儲存服務。本連動驗收須在正式後端完成，不能以「儲存成功」展示提示視為已完成串接。

## 通報及寄送流程

1. 正式平台成功保存通報案件與送出版本後，建立通報完成通知工作；不要在送出前或案件保存失敗時寄送完成通知。
2. 依事件綁定的 `HAZARD_REPORT_SUBMITTED` 代碼取得已啟用、已發布的電子郵件範本。
3. 依當次案件資料計算收件者與副本，並代換主旨、HTML 與純文字內文。
4. 依寄送規格產生當次送出版本的通報資料 PDF，由後端寄信服務寄送。
5. 記錄案件版本、範本代碼及版本、收件人、寄送時間與結果；失敗時可追蹤及重試。

範本修改發布後，新建立的通知工作應採用新版本，不需要修改或重新部署寄信程式。已建立的通知工作及失敗重試使用首次選定的範本版本與當次案件資料，避免同一筆通知重試時內容改變。歷史信件及送出版本保留原有內容。

找不到範本、範本停用或必要參數缺少時，不得寄出含未代換文字的信件，也不得靜默略過。通知工作應保留失敗或待處理狀態，讓維運人員修正後再處理；已成功保存的通報案件不因此被刪除或重複建立。

## 收件設定與範本的分工

- **To**：由案件的填報者電子郵件帶入。
- **Cc**：由案件當次管轄勞動檢查機構的指定收件信箱帶入。
- **寄件者、寄件信箱及 Reply-To**：由核定的郵件服務設定帶入。
- **主旨、說明文字及內文格式**：由「訊息範本維護」管理。
- **通報資料 PDF**：由案件資料產製，對應同一送出版本，不依範本內任意文字改寫案件紀錄。

收件地址不寫死在可編輯的主旨或內文裡。管理者編輯範本文字，不應改變案件管轄或將資料寄到其他收件人。未設定管轄機構指定信箱時，應標示通知設定問題供處理，不得自行猜測或套用其他機構信箱。

## 參數代換

本次交付的範本使用以下參數；資料一律取自通報案件或已核定的服務設定：

- `{PLATFORM_NAME}`：平台名稱。
- `{CASE_NO}`：案件編號。
- `{CASE_VERSION}`：本次送出版本；供通知紀錄使用。
- `{SUBMITTED_AT}`：通報時間，使用臺灣時間。
- `{NOTIFIER_COMPANY}`：事業單位名稱。
- `{CONTRACTOR_UNIT}`：施作單位名稱。
- `{WORK_NAME}`：作業名稱。
- `{DANGEROUS_WORK_ITEMS}`：本次勾選的各項危險作業完整名稱；多項作業逐項列示。
- `{START_DATE}`、`{END_DATE}`：預定作業期間。
- `{LOCATION_SUMMARY}`：本次作業地點摘要。
- `{INSPECTION_OFFICE}`：管轄勞動檢查機構。
- `{CASE_STATUS}`：當次案件狀態，依平台紀錄帶入。
- `{ATTACHMENT_LIST}`：本次附件名稱清單。
- `{REPORT_PDF_FILENAME}`：由案件版本及產製時間建立的通報資料 PDF 檔名。
- `{CASE_URL}`：須登入並具有案件權限的正式案件查詢網址。
- `{INSPECTION_PHONE}`、`{SERVICE_PHONE}`：管轄機構及平台服務電話。

資訊公司須提供可用參數清單及預覽資料，儲存與發布前檢查未知參數。案件名稱、單位名稱及其他文字代入 HTML 時應做文字轉義；案件網址由平台建立並驗證。不得允許範本執行任意程式、查詢密碼或帶出其他案件資料。

## 範本種類及狀態語意

- **通報完成通知**：`HAZARD_REPORT_SUBMITTED`，屬本次已確認需求，於案件成功收件後觸發。
- **變更完成通知**：可另設 `HAZARD_REPORT_CHANGED`，屬延伸設計，觸發時機另行確認。
- **作業取消通知**：可另設 `HAZARD_REPORT_CANCELLED`，屬延伸設計，觸發時機另行確認。

既有示範「案件通報備查通知」與「通報完成通知」不能混用。若未來另行寄送勞檢已閱讀通知，應使用獨立事件及範本。其文字應說明「勞檢已閱讀資料」，不得使用「備查通過」或暗示核准開工。是否寄送閱讀通知仍待決定。

## 連動驗收

1. 管理者在「訊息範本維護」編輯並發布通報完成通知主旨，新測試案件收到的新主旨與修改內容一致，無須改寄信程式。
2. 修改內文後，HTML 與純文字通知均依同一範本版本產生；案件參數正確且沒有未代換的文字。
3. 收件者仍為該案填報者，副本仍為該案管轄機構；範本文字修改不會改變收件規則。
4. 找不到範本、範本停用、缺少參數及寄送失敗均可追蹤，修正後可處理，且不重複建立案件。
5. 修改範本不改變歷史通知；失敗重試使用原工作所記錄的範本版本。
6. 修改、發布、停用與重新啟用有管理權限及操作紀錄；初始設定由指定管理者完成。

資訊公司亦須統一目前原型中展示的範本服務路徑及功能代碼，確保「訊息範本維護」與寄信服務使用同一份正式資料來源。不要因原型內出現不同示意 API 路徑，另建互不相通的範本資料。
